# кандидатогенерация в поиске услуг


итог: 0,875 на лидерборде. 

## 1. данные и что из них следует

| факт | число | что делаем |
|---|---|---|
| корпус холодный | в трейне было только 9,6% объявлений корпуса | вектор объявления считаем из текста, эмбеддинги по `item_id` не учим |
| запросы частично повторяются | 37% текстов запросов бенчмарка есть в трейне | учитываем при сборке валидации |
| правильный ответ почти всегда один | у 85% запросов ровно 1 выбранное объявление | метрика почти бинарная: поймали или нет |
| категория бесполезна | у 99% корпуса категория 114 | не используем |
| локация почти совпадает | у 79% валидационных запросов выбранное объявление в том же `location_id` | главный нетекстовый признак |
| `location_id` это город | медианный разброс координат внутри id 1,3 км, у Москвы и Петербурга 100-200 км | точное совпадение id работает лучше расстояния |
| фильтр вида услуги почти жесткий | вид совпадает у 98% выбранных объявлений, тип только у 79% | вид используем в приоритете, тип только как признак |
| поисков с доставкой нет | 0 в валидации, 0 в бенчмарке | `search_is_delivery_search` не используем |
| негативов в данных нет | трейн это только пары "запрос -> выбранное" | негативы берем из соседей по батчу |

## 2. схема решения

```
запрос
  |
  +- BM25 по заголовку, услугам и описанию, лемматизация pymorphy3
  +- символьные триграммы по заголовку и услугам (опечатки, словоформы)
  +- косинус с дообученным bi-encoder deepvk/USER-bge-m3
  +- популярность, log(число отзывов)
        |
  сумма скоров, считается для каждого из 189 тыс объявлений
        |
  приоритет по локации: свой город -> соседние города -> остальные,
  внутри каждой группы: совпал ли вид услуги с фильтром запроса
        |
  топ-300 по приоритету, внутри по скору
        |
  реранкер: логистическая регрессия, 22 признака на кандидата
        |
  top-50
```

код: `predict.py` собирает ответ, `train.py` обучает bi-encoder, `train_rerank.py` обучает реранкер, `eval_model.py` считает recall на валидации. общая логика в `src/`.

## 3. признаки

### запрос

- `search_query`: нормализуем (нижний регистр, е вместо ё, лишние пробелы), идет в BM25, триграммы и энкодер.
- `search_infm_params_text`: разбираем по словарю названий параметров, достаем вид и тип услуги. вид услуги идет в приоритет. в текст для энкодера фильтры не добавляем, с ними recall@50 zero-shot модели падал с 0,559 до 0,486: короткий запрос тонет в названии категории.
- `search_location_id`: приоритет по локации.

### объявление

- `item_title_raw`: первым в тексте для энкодера, отдельное поле в BM25.
- `item_infm_params_text`: параметры склеены в строку без разделителей, например "Вид услуги Компьютерная помощь Место оказания услуг пр-т Ленина ...". разбираем по словарю из 54 названий (`src/params.py`), достаем вид, тип и список услуг из прайс-листа. список услуг есть у 111 тыс объявлений из 192 тыс и описывает работы теми же словами, что в запросах ("замена термопасты"). адрес, график и цены не используем.
- `item_description_raw`: последним в тексте для энкодера, отдельное поле в BM25. без описания BM25-схема теряет 12 пунктов (0,868 -> 0,746).
- `item_location_id`: приоритет по локации.
- `item_rating_reviews_count`, `item_rating`, `item_price`, флаги контактов, длины текстов, число услуг: только в реранкере.

**соседние города.** 13% выбранных объявлений лежат не в городе запроса. по трейну считаем, в какие чужие `location_id` уходят выборы из данного города. города, куда уходит хотя бы 0,5% выборов, считаем соседними. для Москвы главный сосед 637641, видимо область.

**текст объявления для энкодера**: заголовок, вид услуги, тип услуги, до 25 услуг из прайс-листа, описание (`src/text.py`). модель читает первые 160 токенов, а медиана объявления 299 токенов, поэтому короткие поля идут первыми, описание обрезается. длина 160 выбрана из-за скорости (в 1,6 раза быстрее, чем 256), влияние на качество не проверяли.

## 4. модели

**BM25** (`src/lexical.py`, библиотека bm25s). три поля: заголовок, услуги с видом и типом, описание, веса 1/1/1. веса 3/2/1 и 5/2/1 проверяли, они хуже. лемматизация pymorphy3, после нее ё -> е, иначе "подъемник" из запроса не совпадает с "подъёмник" в объявлении.

**символьные триграммы.** отдельный BM25 по триграммам заголовка и услуг, вес 0,3. ловит "подьемник" -> "подъемник" и словоформы.

**bi-encoder.** `deepvk/USER-bge-m3` (bge-m3, дообученный на русском), дообучен на наших парах:

- 127 488 пар "запрос -> выбранное объявление" из трейна, одна эпоха, 3,8 часа на M4 Pro;
- лосс InfoNCE с in-batch негативами (`CachedMultipleNegativesRankingLoss`), эффективный батч 256, в памяти 16 (GradCache);
- сэмплер без повторов позитива в батче, иначе объявление становится негативом само себе;
- матрица токенов заморожена (половина параметров, словарь XLM-R на 100 языков);
- attention dropout выключен, на MPS он не поддерживается при обучении.

на подмножестве валидации сама модель: recall@50 0,559 -> 0,648 после дообучения.

**реранкер** (`src/rerank.py`). логистическая регрессия, 22 признака на кандидата: скоры BM25, триграмм и dense и их ранги, приоритет по локации, популярность, рейтинг, цена, флаги контактов, длины текстов, число услуг. метка: выбрано или нет. LightGBM lambdarank дал столько же (0,909 против 0,910), взяли логрег, он проще.

## 5. как проверяли качество

**валидация** (`src/split.py`). 2500 запросов из трейна, как в бенчмарке. 37% из них с текстом, который есть в оставшемся трейне, остальные с уникальным текстом, та же пропорция, что в бенчмарке. запрос это пять признаков сразу: текст, город, доставка, фильтры, категория. корпус валидации: все объявления бенчмарка плюс выбранные объявления валидационных запросов, 191 852 штуки.

**метрика** (`src/metrics.py`) сверена с прямой реализацией по формуле из задания.

**реранкер** оценивали по 5 фолдам на запросах валидации.

## 6. найденные ошибки и что с ними сделали

**текст не различает похожие объявления.** по запросу "репетитор по химии" в топе три "Репетитор по химии", а выбрано "Репетитор по биологии и химии ОГЭ". у повторяющихся запросов сотни одинаково подходящих объявлений. что сделали: приоритет по локации. одна перестановка "свой город вперед" внутри топ-200 BM25 дала 0,337 -> 0,505.

**выбранное объявление стоит глубоко по тексту.** recall BM25 на полном корпусе: @200 0,58, @1000 0,82, @3000 0,91. объявление находится, но на 500-3000 месте среди объявлений всей страны. внутри своего города оно высоко: группа "свой город и свой вид услуги" в медиане 8 объявлений. что сделали: считаем скор по всему корпусу и сортируем сначала по приоритету, потом по скору. 0,537 -> 0,813.

| на какой глубине применяем приоритет | recall@50 |
|---|---|
| топ-200 по тексту | 0,537 |
| топ-1000 | 0,724 |
| топ-3000 | 0,785 |
| весь корпус | 0,813 |

**выбранное объявление в соседнем городе.** 13% случаев. что сделали: соседние города по переходам из трейна, 0,813 -> 0,851.

**синонимы и перефразировки.** "ремонт болгарок" -> "Ремонт бензоинструмента электроинструмент", "обследование дома" -> "Технадзор". BM25 такое не находит. что сделали: bi-encoder. на подмножестве с моделью без дообучения 297 запросов в топ-50 находил только dense, 340 только BM25. на полной валидации с дообученной моделью 0,868 -> 0,896.

**опечатки и словоформы.** что сделали: триграммы, +0,7 пункта.

**склеенные параметры без разделителей.** параметр бывает с пустым значением, тогда два названия идут подряд ("Начальная цена Тип стоимости за услугу"). что сделали: парсер по словарю названий, а не по пробелам.

**что не сработало:**

| что пробовали | результат |
|---|---|
| расстояние до центра города вместо точного совпадения `location_id` | 0,75 против 0,81 |
| квота мест для объявлений из чужих городов | не помогает, 0,537 -> 0,534 |
| сортировка внутри группы по числу отзывов вместо текста | хуже |
| память по запросу (что выбирали по этому тексту в трейне) | +1 пункт, не взяли |
| предсказание микрокатегории по тексту запроса | +1 пункт, не взяли |
| вторая эпоха дообучения на тройках с трудными негативами из BM25 | 0,9272 против 0,9276, без прироста |
| реранкер только внутри групп по локации | 0,898 против 0,910 со свободным порядком |

## 8. утечки и ограничения валидации

проверено и в порядке: валидационные запросы полностью изъяты из трейна, дублей `item_id` нет ни в корпусе валидации, ни в бенчмарке, все выбранные объявления валидации есть в ее корпусе, бенчмарк нигде не участвует в обучении. соседние города, модель и реранкер обучены только на трейне.

две проблемы, из-за которых валидация оптимистичнее лидерборда:

1. **утечка пар.** "плиточник, Казань, с фильтром" мог попасть в валидацию, а "плиточник, Казань, без фильтра" с тем же выбранным объявлением остаться в трейне. фильтр в текст запроса не идет, поэтому модель училась на той же паре. таких пар 115 из 2874 (4%).
2. **корпус валидации теплее бенчмарка.** 40,6% выбранных объявлений валидации встречались в трейне у других запросов, в бенчмарке пересечение 9,6%.

поэтому цифры dense-модели и реранкера на валидации завышены. это видно по лидерборду: реранкер дал +0,7 вместо +1,4. на сам лидерборд это не влияет.

`src/split.py` исправлен: теперь из трейна убираются все строки с объявлениями валидации. данные в `data/processed/` пересобраны. модель и реранкер на новом сплите переобучить до сдачи не успели, в `data/models/` лежат те, что дали 0,875. все цифры в этом документе получены на старом сплите.

## 9. воспроизводимость

- `requirements.txt` с версиями, Python 3.12;
- `predict.py` на тех же весах выдает `answer.csv` байт в байт как отправленный, проверено через `cmp`;
- seed зафиксирован в сплите, обучении и реранкере;
- внешних API нет, модели работают локально.

open-source: `deepvk/USER-bge-m3`, sentence-transformers, transformers, torch, bm25s, pymorphy3, scikit-learn, polars, numpy.
